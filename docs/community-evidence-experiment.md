# 社区原文取证：A/B/C 对照

验证两个不同的问题：

1. 四维表示与 claims 锚点能否补回全文召回遗漏的必要原文？比较 B 与 A。
2. 在表示和锚点相同的条件下，社区组织是否有额外作用？比较 C 与 B。

这是已有标注集上的诊断与回归实验，不是未使用过的测试集，也不测回答准确率。

## 三组实现

| 组 | 候选分支 |
| --- | --- |
| A | V2 全文 BM25＋Dense 与问题拆解候选 |
| B | A＋直接按相关维度向量选论文，再按 claims 相似度取原文 |
| C | A＋按社区成员向量中心选社区，在社区内选论文，再按同样的 claims 相似度取原文 |

B、C 共用图中的描述、claims、本地 BGE-M3 编码和原文锚点。不使用社区卡片的额外生成文本。C 只增加社区成员关系的约束，不增加提示词、原文长度或重排槽位。

固定参数：相关维度沿用问题关键词规则；最多选 8 篇论文、24 条 claims、40 条原文窗口。C 最多选 2 个社区。参数在运行前记录，不能根据测试结果挑选最佳组合。

单篇明确问题不启用社区分支，B、C 原样复用 A，逐条核对结果。明确比较多篇论文时，锚点分支仅使用问题中无歧义匹配的论文。

## 共同检索与预算

- 默认全文检索范围为完整 500 篇库，锚点分支覆盖现有 50 篇图论文。三组范围一致。另提供 `--corpus graph50` 作为独立的范围敏感性分析。
- 从原始开发集与 test50 中，预先筛选所有标注证据都在图试点中的可回答题。筛选只决定评测题是否适用，不把 gold 论文传给检索器。当前共 27 题。
- 保留 V2 的问题路由、词汇扩展、全文召回和显式论文子查询。先保留 V2 原有平衡候选的次序，再接完整融合池的剩余候选。
- 两路原文先按文档版本、页码和来源坐标合并身份；使用相同权重的 RRF，再截取最多 40 条。没有预留位置、尾部替换或按标注挑选。
- 三组均只用原问题对“标题＋原文”进行一次统一交叉编码器重排。没有额外 claims CE、facet CE 或公式救援。这是受控实验协议，不能直接与线上默认 20 条、带 facet 重排的历史分数比较。
- 锚点长段落按现有正文的 384-token 窗口、64-token 重叠切开。未把重叠窗口连成大段，未把模型概括作为证据。
- 最终从全部重排候选选择上下文，不再硬砍 top5；预算为 16,000 个序列化证据字符。按源坐标减去已纳入上下文的重复部分，超预算跳过，不按 gold 调整。
- claims 编码是单独记录的离线成本。本地生成模型 API 调用为 0。最终 CE 上限相同不代表总检索成本相同。

## 指标与诊断

主指标：非单篇路由题在预算上下文中的平均必要证据单元覆盖率。

每个问题的覆盖率为“完整命中的必要证据单元数 / 必要单元总数”，再对问题取平均。单元内一个替代方案的全部原文范围都达到 100% 覆盖才算命中；多个替代方案满足任意一个即可。证据齐全率要求该题全部单元命中。

同时报告：

- 合并候选池、进入 CE 的候选、top5 与预算上下文的证据覆盖和论文召回。
- B−A、C−A、C−B 逐题新增与丢失的必要单元。
- 全部现有 claims 锚点的覆盖上限；这只用于离线诊断，不参与候选选择。
- 选中了哪些维度、社区、论文、claims 和原文位置，以及真实新增的原文字数。
- 仅由锚点候选提供的上下文证据、重复范围消除量、实际 CE 对数与用量。
- 延迟分解：公共全文步骤＋各分支与重排、装箱步骤。公共步骤只运行一次以减少重复计算；这是串行阶段测量，不是线上独立请求或并发压测。单篇保护题复用结果，不把复用速度视为加速收益。

按共享 gold 论文的连通分量进行配对 bootstrap。独立论文组少于 10 时，区间只作描述，不下“显著提升”的结论。开放题标注并不穷尽所有正确证据，因此不据此计算证据精确率。

## 执行

仅预览并写入冻结设计清单：

```powershell
python scripts/experiment_community_evidence.py
```

运行三组：

```powershell
python scripts/experiment_community_evidence.py --run
```

中断后使用 `--run --resume <原结果目录>`。索引、图、标注、实验代码、配置的指纹必须保持一致。`--question-ids` 或 `--limit` 用于功能检查；子集结果不能当作完整实验结果。

产物包括 `run.json`、`anchor-bank-ceiling.json`、逐题候选与来源路径、`summary.json`。只读现有索引和图；新缓存与报告写入 `runtime`，不修改首页检索策略。

## 结果如何解释

- B 优于 A、C 与 B 接近：支持结构化表示与锚点取证，不能归功于社区。
- C 稳定优于 B：社区约束可能有额外价值；下一轮再加入同规模随机社区或普通聚类对照。
- 合并池改善但上下文未改善：检查 40 条预筛选、交叉编码器排序与预算选择。
- 锚点总库也没有必要原文：先补充图的源锚点覆盖，不继续调社区排序。
- 任何组出现退化都保留逐题丢失记录。候选取并集并不能保证最终重排、预算上下文不会退化。
